# Telegram delivery implementation checkpoint

Planning: deep; context: canonical actions, owner/account locks, outbox, webhook and provider protocol; verification: transport failure classification, callback ownership/replay, PostgreSQL races and mobile activity; delegation: none. Source implementation is reversible. No bot credential, hosted migration or live recipient is authorized by this document.

The sender must commit dispatch intent before its external call. It then reacquires the owner lock, source/connection row locks and all current policy gates, and holds them through a bounded request. An in-flight Stop serializes against that final authorization. If the process dies or the response is ambiguous, persisted dispatch intent becomes uncertain and is never automatically resent. The generic job handler's retry policy must not be used for notifications.

Transport uses only the fixed Telegram HTTPS endpoint, explicit allowed methods, strict response validation, bounded response size, no redirects, no environment proxy and no automatic retry. Provider URL contains the bot token, so HTTP client debug/info records must be suppressed within the Telegram request context. Errors expose safe classifications only. A successful send must return a matching private chat, bot identity and real message ID. No paid-broadcast parameter is allowed.

Callback buttons use random opaque values (under Telegram's 64-byte bound); only hashes are stored with owner, outbox, action and expiry. Before any action, validate webhook secret, current private chat/sender binding, bot/message identity, connection revision, source revision, token expiry and durable update receipt. Use the existing commitment action service for Done/Working/Help/Snooze. A lost send response can be reconciled only by an authenticated callback carrying its persisted opaque token and the matching bot/chat message. No guessed provider receipt is accepted.

The explicitly labeled **Snooze 1h** button schedules one hour from the click with the owner's timezone; the web app supports custom times. Help records a source-backed draft in the canonical action receipt and shows a generic draft with a source link in Telegram, keeping private details out of the response. Stop remains a revocation path even when new sends are disabled. Callback acknowledgements and message edits occur after the domain commit and never claim the action failed merely because the acknowledgement failed. Duplicate updates may repeat a harmless acknowledgement, never a domain mutation or new push.

The sender has its own default-off flag (`TELEGRAM_DELIVERY_ENABLED`) and requires valid linking/outbox configuration, a secret bot token and an HTTPS frontend origin. A separate lifecycle worker polls at most 20 due items every 15 seconds. A valid provider 429 rejection may retry after its explicit delay, up to three attempts; unknown or unreasonable delays do not retry. Timeouts and all ambiguous sends remain uncertain. Tests use mocked HTTP transport and synthetic records only. Live dedicated-bot configuration and hosted acceptance remain outstanding. The paginated activity API/UI exposes accepted/failed/uncertain history without tokens, chat IDs or full private payloads. Acceptance by Telegram does not imply a read receipt.

Migration 40 adds the attempt ledger and hashed button vault with owner RLS, composite ownership foreign keys and no browser access. Portable exports exclude button secrets; account erasure includes both tables. The sender holds the owner/source locks for its bounded HTTP call (12-second ceiling). Stop takes effect after an already authorized in-flight call resolves; it cannot recall that message. Callback tokens expire after seven days, while `/stop` remains available independently.

Release status: implementation under review; flags remain OFF. Local checks and disposable PostgreSQL CI must be recorded against the new revision. These tests do not establish live provider delivery, webhook configuration, physical-device usability or hosted backup recovery.

Protocol source: [Telegram Bot API](https://core.telegram.org/bots/api), read 2026-10-29: sendMessage returns Message; callback data is 1–64 bytes; answerCallbackQuery dismisses the pending button action; retry_after is provider flood-control guidance.
