# Telegram connection and consent foundation

This slice implements account linking, preferences and revocation only. **No outbound Telegram call exists here. Reminders, Done/Working/Snooze/Help, durable outbox, delivery reconciliation and scheduled briefs remain outstanding.** The UI states this limit and `TELEGRAM_LINKING_ENABLED` defaults to false, including development. No bot credentials, webhook configuration, hosted migration or live recipient was used.

## Flow and boundaries

1. The signed-in owner explicitly creates a link. A random 256-bit nonce expires after ten minutes; only its SHA-256 hash is stored. A replacement link invalidates the previous one. The private link is returned once with `private, no-store` and must not be shared.
2. A secret-authenticated webhook accepts only a private chat whose sender ID equals the chat ID and is not a bot. A group message, edited message, stale nonce or arbitrary unsupported command cannot link an account. The body is bounded to 64 KiB; identifiers use strict integers and Telegram's 52-bit bound.
3. A narrow privileged lookup finds the owner from the nonce hash or established sender/chat hashes. Mutations then use the canonical owner RLS transaction, active-account barrier and connection lock. The nonce is consumed in that transaction. Global unique constraints protect both chat and sender across owners, including simultaneous claims. Conflicts reveal no other account information.
4. Chat/sender IDs are encrypted with the existing token vault helper; HMAC hashes support unique lookup. The development fallback encryption key cannot enable linking. Do not rotate the master key with active bindings: first revoke connections, then rotate and require explicit relinking (or perform a separately reviewed atomic re-encryption/rehash migration). Changing this key without that procedure invalidates lookup/decryption.
5. Linking never grants notification permission. Preferences require an IANA timezone, explicit consent, a version check, a bounded 1–5 daily cap and valid quiet-hour times. Sensitive detail is off by default. These are stored settings; quiet-hour scheduling and actual cap enforcement must be implemented before any sender is enabled.
6. Disconnect or `/stop` clears connection credentials and nonce, advances its revision and revokes notification consent. This remains available with linking disabled. A durable, globally unique update receipt commits atomically with the change; replaying a previous stop cannot disconnect a later binding. Previously unseen stop commands older than the binding are ignored. Late webhook updates cannot reactivate a revoked/closing account. Account erasure includes all three new tables; portable export includes preferences but excludes the connection credential vault and update receipts. Audit events contain only safe IDs, revisions and flags.

## Schema and release

Migration `20261028000037_assistant_connections.sql` is additive. It enables owner RLS and restricts all access to the existing authenticated application-server connection predicate. Direct PostgREST/browser sessions cannot read the vault or forge consent/bindings; implicit anonymous/authenticated grants (including TRUNCATE) are revoked before narrow grants are applied. The runtime schema contract requires these tables, so an approved staging migration must precede this API build. No migration has been applied to hosted staging or production.

After the complete sender/actions implementation is reviewed, the owner must explicitly authorize a dedicated test bot, synthetic recipient, staging configuration/migration and live delivery tests. Set the webhook secret privately using Telegram's `setWebhook`; never paste the bot token into chat or commit it. Verify the bot identity and exact HTTPS webhook, real link/stop flow, callback replay, quiet hours, quota and uncertain deliveries before any pilot flag is enabled. Do not advertise delivery based on synthetic callbacks.
