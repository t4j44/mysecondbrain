# Meeting review snapshot contract

Problem: a confirmation used only `confirmed: true` and optional array indexes. It did not identify the proposals, speaker mappings or context the owner saw. A different tab could change those inputs; a conflicting retry could also receive the first receipt as if its different selection had been accepted.

Recorded-meeting responses now include `review_token`, a SHA-256 fingerprint of meeting identity, title/date/location, project/venture/timezone context, proposals, exact transcript segments and speaker mappings. This is a snapshot identifier, not an authentication token. Authentication and owner/RLS checks remain mandatory. User-authored notes, processing status and receipt fields are excluded because they do not alter the source proposal being confirmed.

Clients send `expected_review_token` when changing speaker mappings, saving reviewed context or confirming candidates. The server checks it after acquiring the canonical capture/meeting locks. Missing or stale snapshots receive 409 with no canonical writes. Context editing retains its existing numeric version check as well. A dirty context editor keeps its original token; polling cannot silently authorize its changes against a different snapshot.

Confirmation receipts retain the reviewed token and normalized requested selection. An identical retry returns that receipt; different selections or tokens receive 409. The browser explains the conflict and requires a manual reload and another explicit save. Reloading replaces stale selections only after the new response arrives; it does not automatically repeat the action or discard unsaved notes.

Deployment compatibility: release the API and web together on approved staging. Older clients omitting the snapshot fail closed with 409 and must reload the updated client. The updated web disables recorded-meeting writes against an older API lacking the token and explains the mismatch. No new database migration or provider configuration is required. Existing historical records and receipts remain readable; this does not implement after-confirmation source correction.

Verification: targeted backend meeting suite passed 83 tests; full local backend passed 483 tests with 19 existing deprecation warnings. Ruff and mypy (171 files) passed. Frontend TypeScript, lint, production build, 91 tests and three synthetic Chromium meeting scenarios passed; the subsequently added conflict-recovery case passed in the focused 15-test meeting component file. Exact-revision CI and real PostgreSQL concurrent confirmation checks require final receipts. The PostgreSQL test covers identical racing requests and conflicting selections under the authenticated owner role. SQLite results do not substitute for those concurrency checks.
