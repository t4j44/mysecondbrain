## 1. Executive System Overview

Taj’s Second Brain is an enterprise-grade, privacy-first Founder Operating System designed to ingest, organize, link, analyze, and retrieve the entirety of a founder’s professional and personal journey. The architecture unites modern responsive UI presentation with asynchronous Python machine-learning backends, cloud database infrastructure, vector semantic indexing, universal plain-text storage portability, and Model Context Protocol (MCP) integrations.

### Design Imperatives
1. **Zero Vendor Lock-in & Universal Data Portability:** All canonical structured data held within cloud relational databases must be perpetually convertible into user-owned, standards-compliant Markdown archives and readable filesystem structures.
2. **Cryptographic Privacy & Strict Isolation:** Every layer—from frontend UI component state down to database SQL evaluation and pgvector neural memory similarity distance calculation—enforces explicit user isolation via Row Level Security (RLS) and cryptographic JWT token verifications.
3. **High-Performance RAG & Grounded Intelligence:** AI synthesis operates purely on verified, user-owned knowledge embeddings. Every assertion generated by the AI assistant or content engine must anchor to immutable database record IDs via verifiable citation metadata.

## 4. Canonical vs. Derived Data Ownership Hierarchy

To resolve data synchronization conflicts across UI inputs, automated background AI worker enriching, and local file system edits, the system enforces a strict unidirectional canonical ownership flow:

```
[Supabase PostgreSQL Database (Canonical Source of Truth)]
                         │
                         ├─ (Triggered on mutation / scheduled background cron)
                         ▼
[Markdown Export Engine (Derived Projection Builder)]
                         │
                         ├─ Writes sanitized file structures
                         ▼
[Local Workspace Directory: `knowledge/Founder_OS/**/*.md`]
                         │
                         ├─ Automatic Background Backup Job
                         ▼
[Google Drive Dedicated Cloud Application Backup Folder]
```

### Operational Rules of Data Truth:
1. **PostgreSQL as Absolute Arbiter:** All CRUD mutations initiated via the web dashboard, mobile devices, or API endpoints immediately write to PostgreSQL. Database transactions establish the immutable sequence of events.
2. **Deterministic Markdown Projections:** The filesystem markdown documents inside `knowledge/Founder_OS/` represent read-only projections. If a user deletes or modifies an exported markdown file manually on their local disk without utilizing an intentional import/restore utility, the background synchronization worker will overwrite the manual filesystem edit with the authentic canonical record from PostgreSQL during the next export cycle.
3. **Disaster Recovery Rehydration:** In the event of complete cloud database corruption or hosting migration, the system executes a reversal rehydration routine: the database schema is re-created from scratch, and an ingestion parser scans the YAML frontmatter of `knowledge/Founder_OS/**/*.md` to reconstruct all primary keys, timestamps, relationships, and table entries with 100% fidelity.

## 5. Deployment & Containerization Architecture

### Frontend Edge Deployment
- **Target Provider:** Vercel (Next.js Application Architecture).
- **Execution Strategy:** React Server Components (RSC) evaluate in secure Vercel Node.js Server environments; Static components are globally edge-cached via CDN; API requests pass directly to the backend domain via custom reverse domain routing (`https://app.tajssecondbrain.ai` -> `https://api.tajssecondbrain.ai`).
- **Environment Management:** Build-time injected safe keys (`NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `NEXT_PUBLIC_API_BASE_URL`).

### Backend & MCP Server Deployment (Evaluated Choice: Render / Railway Container Cluster)
- **Target Provider Selection:** **Render (Recommended Primary)** or **Railway (Recommended Alternative)** running containerized Linux deployments.
- **Why Not Vercel for FastAPI?** Python FastAPI implementations hosted on Vercel Serverless Functions experience severe cold-start latency (3-8 seconds for heavy machine-learning libraries like Pydantic and SQLAlchemy), lack long-running execution workers for document processing, and drop Server-Sent Event (SSE) streaming connections during lengthy LLM analysis cycles.
- **Container Strategy:** Docker-orchestrated multi-stage builds cleanly encapsulating Python UV virtual environments, compiled native pgvector bindings, and OpenSSL crypto dependencies.

```dockerfile
# Concept Blueprint: Unified Service Deployment
FROM python:3.11-slim as backend-runtime
WORKDIR /app
COPY pyproject.toml requirements.txt ./
RUN pip install --no-cache-dir -r requirements.txt
COPY ./backend ./backend
EXPOSE 8000
# Startup invokes Uvicorn production ASGI server with optimized worker processes
CMD ["uvicorn", "backend.main:app", "--host", "0.0.0.0", "--port", "8000", "--workers", "4", "--proxy-headers"]
```

### Scaling & High-Availability Operations
- **Stateless Application Tier:** Both Next.js server routers and FastAPI application instances remain purely stateless. All conversational memory sessions reside in PostgreSQL tables, enabling instant horizontal pod scaling under traffic surges.
- **Connection Pooling:** All SQLAlchemy database sessions route through **Supabase Supavisor / PgBouncer TCP Connection Pools** using Session or Transaction pooling modes to prevent connection exhaustion under asynchronous worker concurrency.
